Source documentation for version 00.13.03

Reviewed September 26, 2026. Application version 00.13.03. Security and ChatGPT behavior requires deploying the matching source release; this site is not the task API.

Authentication and session controls

New passwords use Argon2id (64 MiB, three iterations, one lane). Existing Passlib PBKDF2-SHA256 records are verified by a bounded compatibility reader and migrate on successful login; Passlib and python-jose are no longer runtime dependencies. HTTP login never recovers or promotes administrators. Password changes invalidate sessions, API access tokens, and integration tokens. Web forms and same-origin fetch writes require CSRF tokens; logout is a POST operation.

Server-side authorization

Original API operations re-read current user roles and enforce their existing ownership/admin rules. The ChatGPT interface separately enforces task ownership, even for administrator-issued integration tokens. Request bodies, credential lengths, task list pages, notification response sizes, and login attempts are bounded. Reverse-proxy limits are still necessary for public deployments.

Network and data controls

Notification transport checks destination DNS/IPs, pins the validated address, verifies TLS, rejects redirects and unsafe headers, and blocks metadata/loopback destinations. Exact operator allowlists support trusted LAN services. Windows notification channel URIs must use the expected Microsoft hostname family before a bearer credential is attached. Notification API output redacts credentials; backup/settings/initial-password files use owner-only atomic writes.

Known residual risks

The browser Content Security Policy still allows inline scripts/styles because existing templates rely on them; conversion to external scripts or per-response nonces is separate work. Credentials stored in the application database and exported backups are not automatically encrypted at rest. The rate limiter and scheduler are process-local. Notification socket timeouts are not a guarantee of a strict wall-clock deadline for every DNS/provider failure. Upstream advisories, provider APIs, and base images can change after an audit.

Automated dependency scanning does not establish absence of exploitable vulnerabilities. The original ecdsa advisory was a transitive dependency finding; this application used HS256, so that advisory alone did not demonstrate an exploitable ECDSA signing path. Removing the unused crypto stack reduces that exposure without inventing an exploit claim.

Validation scope

The repository workflow runs regression tests, dependency and static scans, docs checks, browser smoke tests, and container checks. Consult the exact commit's run and artifacts rather than historical validation reports. Provider delivery, real-data disaster recovery, penetration testing of a deployed host, accessibility auditing, and live ChatGPT acceptance require separate environment-specific evidence.

Reporting

Report suspected vulnerabilities privately to the repository owner, using GitHub's private vulnerability-reporting facility when enabled. Do not place credentials or detailed unpatched deployment exploit information in public issues. The source audit and fix/deprecate decisions are recorded in AUDIT_REPORT.md.
